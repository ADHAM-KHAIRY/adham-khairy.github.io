CyCTF Luxor Mobile writeup

Mar 16, 2026 · 9 min read
ctf-writeupmobile-pentestingandroid-pentesting

In this write-up, I document my slightly sleep-deprived journey through the Mobile challenges of Luxor Cyshield CTF 2026. It covers the full process: the tools I threw at the problems, the analysis that followed, and the exploits that eventually bullied the challenges into giving up their flags. The steps are clear enough that anyone can replicate the process without sacrificing too many brain cells.

Phase 1: Qualification Round (Quals)

Challenge: Phantom Prefs
Category: Android

At first glance, the app greets us with a classic login screen patiently waiting for a username and password, like it actually believes we’re going to log in the normal way.

After peeking at the MainActivity source code, we find the real gatekeeper logic. The app expects the username to be phantom_admin, and the password must start with dbg_. If that condition is satisfied, the app takes the rest of the password (everything after dbg_) and feeds it into LegacyDecoder().resolve(password.substring(4)).

public void attemptLogin() {
        String username = this.etUsername.getText().toString().trim();
        String password = this.etPassword.getText().toString().trim();
        if (username.isEmpty() || password.isEmpty()) {
            Toast.makeText(this, "Please enter credentials", 0).show();
            return;
        }
        if (username.equals("phantom_admin") && password.startsWith("dbg_")) {
            String adminToken = new LegacyDecoder().resolve(password.substring(4));
            if (!adminToken.isEmpty()) {
                Toast.makeText(this, "Debug session: " + adminToken, 1).show();
                return;
            } else {
                Toast.makeText(this, "Invalid debug token", 0).show();
                return;
            }
        }

So naturally, the next step was diving into the LegacyDecoder source code. The resolve function looked suspiciously simple: it decodes the input using Base64, XORs the result with the value 66, and then runs it through a hardcoded hash function to generate a token. Sounds promising, right? Unfortunately, this entire path turned out to be a classic CTF rabbit hole, rewarding the effort with the very motivational flag: CyCTF{fake_flag_nice_try}.

public class LegacyDecoder {
    private static final byte DECODE_KEY = 66
    public String getStoredHash() {
        return "ATsBFgQ5JCMpJx0kLiMlHSwrIScdNjA7Pw==";
    }
    public String resolve(String input) {
        try {
            String hash = getStoredHash();
            byte[] decoded = Base64.decode(hash, 0);
            byte[] result = new byte[decoded.length];
            for (int i = 0; i < decoded.length; i++) {
                result[i] = (byte) (decoded[i] ^ DECODE_KEY);
            }
            String token = new String(result);
            if (input != null) {
                if (input.equals(token)) {
                    return token;
                }
            }
            return "";
        } catch (Exception e) {
            return "";
        }
    }

But while digging deeper into MainActivity, something interesting showed up. There’s a chunk of code that never actually gets called during normal execution… which, in CTF terms, usually means “hey hacker, look here.” This hidden snippet creates a ShadowContext, accesses getSharedPreferences("session_store", 0), and then retrieves the stored admin session hash. After that, it decodes the value, hinting that the real secret might be hiding inside the app’s stored session data rather than the fake decoder rabbit hole.

ShadowContext shadowCtx = new ShadowContext(this);
SharedPreferences prefs = shadowCtx.getSharedPreferences("session_store", 0);
String sessionHash = prefs.getString("session_token_hash", "");
if (sessionHash != null && !sessionHash.isEmpty()) {
            String decoded = shadowCtx.decodeSessionToken(sessionHash);
            if (password.equals(decoded)) {
                Toast.makeText(this, "Welcome back, " + username, 1).show();
                return;
            } else {
                Toast.makeText(this, "Invalid credentials", 0).show();
                return;
            }
        }
        Toast.makeText(this, "Session expired. Contact admin.", 0).show();

Digging into the source code of ShadowContext, things start getting interesting. The class secretly creates a prefs_backup.xml file inside a hidden directory at .config/.system. Totally normal behavior… definitely not suspicious at all. Inside this logic, we also find the secret key used for the XOR operation, which happens to be the value 66. The decodeSessionToken function simply takes the input, decodes it from Base64, and then XORs every byte with 66, revealing the original session token.

public class ShadowContext extends ContextWrapper {
    private static final byte DECODE_KEY = 66;
    private static final String PREFS_FILE = "prefs_backup";
    private static final String SHADOW_DIR = ".config/.system";
    public String decodeSessionToken(String encodedToken) {
        byte[] decoded = Base64.decode(encodedToken, 0);
        byte[] result = new byte[decoded.length];
        for (int i = 0; i < decoded.length; i++) {
            result[i] = (byte) (decoded[i] ^ DECODE_KEY);
        }
        return new String(result);
    }
}

At this point, the mission becomes pretty straightforward. All that’s left is to check the hidden directory and grab the stored session token. By running cat /data/data/com.ctf.phantomprefs/files/.config/.system, we can locate the session_token_hash. After extracting it, we simply apply the decoding logic we discovered earlier to reveal the real flag.

Challenge: HighScoreHero
Category: Android

We’re handed a single file: highscorehero.apk. The app itself is a dead-simple mobile game — tap a button, watch your score go up, compete on a leaderboard. No login screen, no network calls, nothing obviously CTF-shaped on the surface. Just four players on a leaderboard and a button that hands out points.

The first thing any self-respecting reverse engineer does is extract the APK and throw the asset file at protoc:

Four normal players — name and score, nothing surprising. But that first entry is strange. SYSTEM has no score, and instead of a second field it carries 48 bytes of binary data in field 3. That's not a coincidence. That's the flag.

Time to pull out Jadx and see what the app actually does with that blob:

Three classes do all the interesting work: CryptoHelper, LegacyScoreManager, and ScoreManager. Let's go through them.

The static initializer of CryptoHelper immediately hands us two hardcoded byte arrays via fill-array-data-payload instructions:

LEGACY_IV          = 00 01 02 03 04 05 06 07 08 09 0a 0b 0c 0d 0e 0f
DEBUG_FALLBACK_KEY = fe 0e 25 e2 75 a8 0c 35 eb 12 33 0b 9c 01 fc 42

The class has two cipher modes. decrypt() uses AES/CBC/PKCS7 with LEGACY_IV. And then there's processBlock(), which uses AES/ECB/PKCS5 — no IV, just raw block cipher. That second one is going to matter a lot later.

The deriveKey() method computes SHA-256(certHash + KEY_SALT)[:16] and returns the result. If anything throws an exception — say, a cert check failing in a debug environment — it quietly falls back to returning DEBUG_FALLBACK_KEY directly.

Here’s where things get interesting, and where the first rabbit hole opens up.

The static initializer of LegacyScoreManager reveals a key salt:

KEY_SALT = b'ctf.hsh'

And there’s a method called extractSystemToken(). Its logic, paraphrased:

1. Load scoreboard from score_cache.pb
2. Derive key = SHA-256(certHash + "ctf.hsh")[:16]
3. Find the SYSTEM entry
4. Call entry.getMetadata()   <-- proto field 4
5. If metadata.length > 0: decrypt it and return the string

Notice it calls getMetadata() — that's proto field 4 — not getScoreHash() which is field 3. So the natural assumption is: the 48-byte blob must be in field 4, and we just need to find it and decrypt it with the right key.

Except… protoc --decode_raw only shows a field 3 in that SYSTEM entry. No field 4 anywhere. And there's no score_cache.pb on the device either — only scores.pb exists in /data/data/com.ctf.highscorehero/files/.

The method references loadScores(), which reads score_cache.pb. That file is never written by the app. So extractSystemToken() would always return an empty string in practice — it's dead code with a very deliberate purpose: to mislead.

After chasing the metadata rabbit hole for a while and coming up empty, it's time to look at the other method: verifyScoreHash(). This one actually runs during normal app execution.

Its logic:

1. key       = deriveKey(certHash, KEY_SALT)
2. plaintext = decrypt(entry.getScoreHash(), key)
3. return plaintext.trim().equals(entry.getPlayerName())

So score_hash (field 3) stores AES-CBC(playerName, certKey, LEGACY_IV). For a regular player like xXDragonSlayerXx, their 16-byte score_hash decrypts to their username. That's the integrity check.

For the SYSTEM entry, the score_hash is 48 bytes — three full AES blocks. The SYSTEM player has no username to verify against. Its score_hash contains something else entirely.

Looking at the fallback key more carefully:

cert SHA-256 (first 16 bytes): fe 0e 25 e2 75 a8 0c 35 eb 12 33 0b 9c 01 fc 10
DEBUG_FALLBACK_KEY:            fe 0e 25 e2 75 a8 0c 35 eb 12 33 0b 9c 01 fc 42
                                                                         ^^
                                              only the last byte differs (0x10 vs 0x42)

That is not a coincidence. The DEBUG_FALLBACK_KEY is deliberately set to be almost identical to the first 16 bytes of the APK signing certificate's SHA-256. The challenge author is pointing directly at the real key: cert_sha256[:16].

Now that the key is clear, there’s one last piece: which cipher mode? We tried AES-CBC with LEGACY_IV — gibberish. But the app has a second cipher mode: processBlock(), which uses AES-ECB with no IV.

Challenge: Shadow
Category: Android

First look at the APK’s UI? Blank. Empty. Nothing to click, nothing to poke… just me going “Hmmm, okay then.”

Oh, and one small detail I almost forgot… to actually get the flag, you need to build your own APK to exploit the target app and upload it to the CTF providers. Yep, this challenge literally makes you fight APK with APK.

So the first place to check is the AndroidManifest.xml. While scrolling through it, something spicy shows up: an exported service. And not just any service…

<service
    android:name="com.ctf.shadow.service.ShadowService"
    android:permission="com.ctf.shadow.ACCESS_SHADOW"
    android:exported="true"/>
<permission
        android:name="com.ctf.shadow.ACCESS_SHADOW"
        android:protectionLevel="normal"/>

An exported service in a CTF? Yeah… that’s basically the app saying: “Hey hackers, come poke me.” So obviously, the next step is to dive into the ShadowService code and see what secrets it’s hiding.

Inspecting ShadowService reveals the core vulnerability inside the onTransact() handler. The service exposes a Binder transaction TRANSACTION_GET_SECRET (1338) that processes incoming IPC requests.

The logic expects two parameters from the caller:

  • claimedUid
  • action
int claimedUid = data.readInt();
String action = data.readString();

It then performs the following check:

if ("get_flag".equals(action) && claimedUid == 1000)

If this condition is satisfied, the service returns the flag:

reply.writeString(FlagStore.getFlag());

The critical issue is that claimedUid is read directly from the Parcel supplied by the caller. Since Parcel data is fully controlled by the calling application, this value can be arbitrarily forged.

Although the service logs the real caller identity using:

Binder.getCallingUid()

it never uses this value for the access control check.

This creates a classic Broken Access Control / Improper Authorization vulnerability in Binder IPC. Any external application can invoke the transaction, provide claimedUid = 1000, set action = "get_flag", and successfully retrieve the flag.

With the vulnerability understood, the next step is crafting an exploit APK that abuses this broken access control.

The exploit APK needs to do three things:

  1. Declare com.ctf.shadow.ACCESS_SHADOW permission — since it's protectionLevel=normal, any app can request it
  2. Declare a <queries> tag for com.ctf.shadow to make it visible (required for targetSdk ≥ 30)
  3. Bind to ShadowService and send the crafted Parcel

The manifest handles the first two:

<queries>
    <package android:name="com.ctf.shadow" />
</queries>
<uses-permission android:name="com.ctf.shadow.ACCESS_SHADOW" />

Now for the actual exploit. Once the app binds to ShadowService, Android delivers an IBinder handle via onServiceConnected(). At that point we bypass all AIDL abstractions and craft the raw Parcel manually:

data.writeInterfaceToken(DESCRIPTOR);  // passes enforceInterface() check
data.writeInt(CLAIMED_UID);            // lie — claim we are UID 1000
data.writeString("get_flag");          // passes the action check
binder.transact(TX_GET_SECRET, data, reply, 0);

Three lines is all it takes. We pass the interface token to satisfy enforceInterface(), write 1000 as our fake UID, and set the action to "get_flag". The service happily accepts all of this since it never cross-checks with Binder.getCallingUid().

The response comes back in reply:

reply.readException();
String flag = reply.readString();

No crash, no access denied — just the flag.

And that’s a wrap for the quals! 🏁 Nothing else, folks. Now we wait… patiently… for the finals to drop so I can nerd out here again.
