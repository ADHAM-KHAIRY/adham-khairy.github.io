[Tob] WEB challenge — Helwan CTF

Hi — I’m Adham (aka 0xSponge). My team ( أدهم عايز يتجوز ) placed 4th in the Helwan CTF; I solved three web challenges solo. This writeup covers the Last one, with clear recon, exploit POCs, and the final flags.

On loading the Tob challenge I observed two primary features: a place to compose notes and a separate action to submit those notes to an automated bot for review.

Now I’ll try a basic XSS payload to see where the input is reflected.

In the page source I noticed < and > were being escaped to &lt; and &gt;. The payload is reflected in four places, and the most interesting reflection appears inside a <script> block.

php
$content = str_replace(array('<', '>'), array('&lt;', '&gt;'), $content);
$title = str_replace(array('<', '>'), array('&lt;', '&gt;'), $title);
$category = str_replace(array('<', '>'), array('&lt;', '&gt;'), $category);

I crafted another payload aimed at the <script> context and tested it.

Although the payload looks fine, the alert never fired.

Hmm — something’s off. I’ll open the browser console to check for errors.

The console reports secure is not defined. That means the injected snippet secure.validate('remove', ''); alert(''); throws before alert() can run.

After a lot of searching I found a blog post that describes this exact scenario.

XSS Exception Bypass using Hoisting 🧙‍♂️

The blog explains hoisting, a JavaScript feature where function and variable declarations are moved to the top of their scope before code runs. Think of it like a backstage pass — you can access things before they’re officially declared. Normally, x.y() would throw a ReferenceError if x is undefined, which blocks execution.

The solution is to declare a secure function so it gets hoisted. This makes secure.validate() return undefined, which doesn’t matter — the key point is that our injected code executes successfully.

Next, I tested the payload:

javascript
', alert()); 
function secure() {}; 
secure('

to see if it executes and how the browser interprets it.

javascript
<script>
secure.validate('remove', '', alert());
function secure () {}; 
secure('');
</script>

Inspecting the docker-compose.yml, I found that the bot’s cookies are stored at http://proxy
